ABSTRACT

Conventional library operations in educational institutions often rely on manual ledger books or disconnected spreadsheets, which are prone to data inconsistency, miscounted book copies, and error-prone manual calculation of overdue penalties. For small and medium-sized college libraries, a simple, reliable, and easily deployable tool is needed that does not require a database server or expensive software.

This project presents the “LIBRARY MANAGEMENT SYSTEM,” a terminal-based circulation and inventory management application built with Python Object-Oriented Programming (OOP) and backed by lightweight JSON file storage. The system models core library entities through the Book and Student classes, while the Library class manages data loading, saving, validation, and all circulation operations. The entire application is contained in a single main.py file and uses only the Python standard library.

Key features include: (1) Validated Catalog Management that checks author names using regular expressions and merges duplicate titles by increasing the copy count; (2) Derived Availability Tracking in which available copies are calculated from active issue transactions instead of being stored separately; (3) Issue and Return Workflow with date validation and an automatic overdue fine of ₹5 per day calculated at the time of return; and (4) Search, History and Statistics offering partial-match book search, a transaction history sorted by latest issue, and a summary of the most frequently issued titles.

The software was validated through manual functional testing of every menu option using valid, invalid, and boundary inputs, confirming correct input validation, accurate fine calculation, persistence of records across program restarts, and graceful handling of missing or corrupted data files.

Keywords: Library Management System, Object-Oriented Programming (OOP), JSON Data Storage, Book Circulation, Overdue Fine Calculation, Command-Line Interface (CLI), Input Validation.

CHAPTER 1
INTRODUCTION

Academic libraries form the intellectual nucleus of higher education institutions, serving hundreds of students and faculty members daily. In many college departments, circulation operations—such as catalog tracking, book checkouts, returns, and overdue fee collections—are still conducted through manual paper ledgers or obsolete monolithic systems. These legacy workflows suffer from severe record discrepancies, untracked inventory depletion, and delayed financial settlement of library dues.

The LIBRARY MANAGEMENT SYSTEM is engineered as a lightweight, terminal-driven automation tool built using Python Object-Oriented Programming (OOP) and JSON file storage. Operating in a continuous interactive menu loop, the application integrates catalog management, student registration, book issue and return, overdue fine calculation, searching, and library statistics into a single, zero-dependency program.

Table 1.1: Library Management System Operational Capabilities & Scope Overview
Module Feature Scope Underlying Entity Module Feature Scope Underlying Entity
Catalog Add books, merge duplicates, track copies Book Fines Overdue days × ₹5 calculated at return Fine Field
Members Register students, unique email validation Student History Transactions sorted by latest issue Transaction
Circulation Issue with due date, return by transaction ID Transaction Analytics Totals, availability, top issued titles Statistics

* The due date is entered by the librarian at the time of issue (it cannot be in the past); the overdue fine accrues at ₹5/day.

The system emphasizes data reliability and simple operation: every input is validated before it is accepted, unique IDs are generated automatically and displayed to the user, all lookups are case-insensitive, and records are written to the data/ folder immediately after every change, so no information is lost between sessions.

CHAPTER 2
OBJECTIVES

The project was designed to satisfy key educational and operational objectives, bridging clean software design principles with real-world practical utility:

2.1 Primary Objective

To design, implement, and test a terminal-based library management program in Python using Object-Oriented Programming, loops, conditional branching, regular expressions, date handling, JSON file persistence, and exception handling.

2.2 Functional & Technical Objectives

• OOP Modeling: Construct encapsulated domain classes (Book, Student, and Library) with a clear separation between data records, business rules, and console interaction.
• Reliable Data Persistence: Store books, students, and transactions in JSON files that are loaded at startup and saved after every change.
• Accurate Availability Tracking: Calculate available copies from active issue records so that stock counts can never drift out of sync.
• Automated Fine Calculation: Compute overdue days on return and charge ₹5/day (FINE_PER_DAY), recording the fine in the transaction.
• Input Validation & Fault Tolerance: Validate names, emails, quantities, and dates, and handle missing or corrupted data files without crashing.

3.2 Risk Mitigation & Quality Planning

Risk 1: Inventory Mismatch: Mitigated by never storing an available-copies counter; available_copies() derives it from the number of active Issued transactions and issuing is blocked when fewer than one copy remains.
Risk 2: Missing or Corrupted Data Files: Solved through load_data(), which creates missing files, catches JSONDecodeError and OSError, and starts with an empty list instead of crashing.
Risk 3: Invalid User Input: Addressed by validating every input (regular expression, integer and date parsing) and wrapping each menu action in a try-except block inside main().

CHAPTER 7
SYSTEM MECHANISM, WORKFLOW & DATA HANDLING
7.1 End-to-End System Workflow (How the Application Works)

The continuous execution cycle within main.py operates through eight sequential stages:

Step Workflow Phase Underlying System Operations & Actions
1 Initialization main() creates the Library object; its constructor creates the data/ folder and loads the books, students, and transactions JSON files (creating empty files if missing).
2 Menu Dispatching Displays 11 choices (0–10). The input is stripped and mapped to Library methods through an action dictionary; invalid choices show a message.
3 Inventory Ingestion Option [1] prompts for Title, Author (letters and spaces only), and Copies (≥ 1); a matching title and author increases the quantity, otherwise a new book with ID B + timestamp is saved.
4 Member Registration Option [5] registers students with a non-blank name and a unique email containing “@”, storing them with ID S + timestamp.
5 Book Issue Option [7] validates book and student IDs and availability (copies ≥ 1), reads a due date (YYYY-MM-DD, not in the past), and appends an Issued transaction with ID T + timestamp.
6 Return & Overdue Fine Option [8] takes the transaction ID, calculates overdue days against the due date, sets the fine (₹5/day), and marks the transaction Returned.
7 Display & Search Options [2]–[4], [6], and [9] show all books, available books, search results, registered students, and the transaction history (newest first).
8 Statistics & Exit Option [10] reports totals, available and issued copies, student count, and the top five issued titles; option [0] saves all records and exits.

7.2 Core Circulation Engine & Fine Calculation

The circulation engine executes simple, deterministic logic. When a transaction is returned, the Library.return_book() method compares the recorded due date with the actual return date:

Overdue Days = max(0, (Return Date - Due Date).days)
Fine = Overdue Days × FINE_PER_DAY (₹5)
Status = "Returned"

The calculated fine, the return date, and the new status are written into the transaction record, and the overdue days and fine amount are displayed on screen. Because available copies are computed as quantity − issued transactions, marking a transaction as Returned automatically makes the copy available again.

CHAPTER 8
CHALLENGES & PROBLEMS FACED DURING DEVELOPMENT

Engineering a dependable terminal software environment required resolving several key technical challenges:

8.1 Keeping Book Availability Consistent

Problem: Storing an “available copies” counter beside the total quantity could drift out of sync with the actual issue records after edits or interrupted runs.
Solution: Availability is never stored; available_copies() calculates it as the total quantity minus the number of Issued transactions for that book.

8.2 Overdue Calculation Boundary Edge Cases

Problem: Returning a book early or exactly on the due date produces a zero or negative date difference, which must never create a fine.
Solution: Dates are stored in ISO format and converted with date.fromisoformat(); the overdue days are clamped using max(0, ...) so only late returns are charged.

8.3 Missing or Corrupted Data Files

Problem: On the first run the JSON files do not exist, and a damaged file would normally crash the program with a decoding error.
Solution: load_data() creates empty files when they are missing, catches JSONDecodeError and OSError, prints a warning, and continues with an empty list.

8.4 Unique IDs and Input Validation

Problem: Without a database, unique IDs had to be generated by the program, and incorrect inputs (such as numbers in author names or invalid dates) could corrupt records.
Solution: IDs are built from a prefix and a timestamp (B, S, T + yymmddHHMMSS), author names are checked with a regular expression, and dates and quantities are parsed inside try-except blocks.

APPENDIX B: SAMPLE CODE & CORE IMPLEMENTATION

Code B.1: Return Book & Overdue Fine Logic (main.py)
def return_book(self):
    transaction_id = input("Enter transaction ID: ").strip()
    transaction = next((item for item in self.transactions
                        if item["id"].lower() == transaction_id.lower()), None)
    if transaction is None:
        print("Error: Invalid transaction ID.")
        return
    if transaction["status"] != "Issued":
        print("This book has already been returned.")
        return
    returned_date = date.today()
    due_date = date.fromisoformat(transaction["due_date"])
    overdue_days = max(0, (returned_date - due_date).days)
    fine = overdue_days * FINE_PER_DAY
    transaction["returned_on"] = returned_date.isoformat()
    transaction["fine"] = fine
    transaction["status"] = "Returned"
    self.save_all()
Code B.2: Available Copies Calculation (main.py)
def available_copies(self, book_id):
    book = self.find_book(book_id)
    if book is None:
        return 0
    issued_count = sum(1 for transaction in self.transactions
                       if transaction["book_id"] == book_id
                       and transaction["status"] == "Issued")
    return max(0, book["quantity"] - issued_count)
